# Coze 工作流自动生成与修复 Agent 技术方案评审

> 评审对象：[coze-workflow-agent-technical-plan.md](./coze-workflow-agent-technical-plan.md)
> 配套材料：[Ai agent自动生成工作流模版.md](./Ai%20agent自动生成工作流模版.md)

---

### 1. 总体结论

- **一句话结论**：架构骨架（解析→规划→生成→校验→执行→修复）方向正确，但当前方案只是"单向管道"的可行性论证，离"稳定闭环"还差两个硬前提：读取接口和试运行结果/日志接口；方案的"自动修复闭环"部分属于纸面设计。
- **可行性评级**：**中**。MVP（create/save/test_run 跑通）为高；带读取、日志、模板字典的稳定编辑与修复为中；"全自动生成任意复杂工作流并自修复"为低。
- **最大风险点**：试运行结果无法查询 → 修复器没有输入，闭环断在最关键一环；其次是平台契约不透明（commit 语义、submit_commit_id 来源、session 过期、节点类型与字段无字典），会让"不编造平台未知字段"这条原则无法执行。

### 2. 详细评审

#### 问题 1：整体架构是否合理？

**结论**：合理但不完整。五段式本身没问题，缺少的是横切层：状态/版本管理、鉴权/会话管理、持久化与审计、评估与人工接管点。

**依据**：从配套抓包文件可以看到几个方案没有覆盖的事实：save 依赖 `submit_commit_id`（一个真实的版本号），test_run 依赖 `commit_id`，会话是 24 小时过期的 cookie session。这说明平台有明确的"版本/提交"模型，而方案里完全没有"当前在哪个 commit 上编辑、保存后状态怎么迁移"这一层；没有它，编辑和修复的基线都不存在。

**风险**：架构图画了"试运行结果分析"模块，但 8.2 又承认缺日志接口——画了闭环、没有闭环的输入，属于自相矛盾。另外没有人工确认点：auto-save 会直接覆盖草稿/版本状态，企业环境里这是不可接受的默认行为。

**改进建议**：改成状态机式架构：`READ → PLAN → RENDER → VALIDATE → COMMIT(save) → RUN → OBSERVE(查日志) → REPAIR(循环)`，并横切三件事——会话管理、每次保存前的版本快照、覆盖/发布前的人工确认。把"试运行结果分析"明确标注为依赖日志接口，未接通前不进入修复循环。

#### 问题 2："先规划草图，再生成 Coze JSON"的分层是否必要？有没有更好的方式？

**结论**：分层必要，但方案的第二层到第三层存在关键歧义，这是它最大的缺陷；有更好的方式。

**依据**：直接让 LLM 一次性吐最终 JSON 的失败模式非常具体：节点 `type` 是平台数字编码（样例里 start=1、end=2、查询数据=43），边字段是 `sourceNodeID/targetNodeID` 而不是草图的 `from/to`，变量引用是 `block-output` + `blockID` 的嵌套结构。LLM 在这些细节上每步都有出错机会，所以"先抽象再落地"是对的。但方案 4 里写"最后把草图转换成平台 schema"，6.3 又写"再由程序转换为 Coze 需要的最终格式"——到底是谁转换？如果还是 LLM，那么分层只减少了一半风险（规划错了还是错，字段错误照样发生）。

**风险**：草图层（`llm/code/branch` 这种语义名）和平台层（`type: "43"`）之间存在一层映射，这层映射如果不确定性执行，第二层草图的收益会被抵消。

**改进建议**：明确三层职责——LLM 只输出第 1、2 层（需求摘要 + 声明式草图，节点类型用白名单枚举、参数值用表单式字段），第 2 层到平台 schema 由**确定性代码**（模板渲染器 + 字典映射）完成。即"LLM 生成中间表示（IR），程序做 schema 投影"。这才是比"LLM 先生成草图、再让 LLM 生成 JSON"更稳的方式：随机性的边界被收敛到"选什么节点、填什么参数"，而不是"写什么字段名"。

#### 问题 3：Prompt 设计是否足够稳？哪里容易失控？

**结论**：不够稳。方案把"输出必须是严格可解析的 JSON"当成提示词约束，这在工程上属于把稳定性寄托在模型行为上。

**依据**：即使模型遵守"只输出 JSON"，失控点依然很多：节点 `type` 写成字符串还是数字、`ref` 嵌套结构写错、引用了不存在的 `blockID`（变量悬空）、`data.inputs` 里的字段名与平台模板不一致、中文标点/注释混入 JSON、分支边的端口字段缺失。这些都不是"格式约束提示词"能解决的，需要**结构性约束**（JSON Schema / response_format / 工具参数绑定）+ **校验器兜底** + **带校验错误的反馈重试**。

**风险**：最易失控的是**变量引用**——start 节点 outputs 定义了可用变量，后续节点 ref 必须指向真实上游的 blockID 和 output 名。方案里完全没有变量作用域校验，这是修复器会反复踩的坑。其次是**参数值**（LLM 编造模板里不存在的配置字段）。

**改进建议**：不给 LLM 自由写 `data` 的自由度。每个节点类型做成"参数表单"（如 LLM 节点只有 prompt、model、temperature、输入变量映射可填），其余结构由模板填充；输出用 JSON Schema 强约束；校验器报错时带 `field_path`，反馈给模型做一次重试。提示词里"不要编造平台未知字段"这种原则只有在有字段字典时才可执行。

#### 问题 4：用 MCP 调用 create/save/test_run 的闭环是否完整？

**结论**：不完整。三个工具只覆盖"发起"，没有覆盖"确认"。

**依据**：三点硬伤：一是 test_run 只返回 `execute_id`，执行是异步的（LLM 节点可能跑几十秒），方案没有结果查询和轮询工具，"试运行验证"实际只是"发起了试运行"；二是 save 需要 `submit_commit_id`，方案没说明它从哪来（必须来自读取当前工作流版本），这是编辑和保存的隐含前置依赖；三是 test_run 的 `commit_id` 语义未确认——它决定你跑的是草稿还是某个已提交版本，方案没讨论。

**风险**：没有结果查询时，修复器面对的是 `execute_id` 而不是错误信息，整个修复循环无输入；没有 `submit_commit_id` 获取逻辑，第二次 save 就可能因 commit 过期/不匹配失败（`remaining_ttl: 900` 暗示存在某种 TTL 语义，含义未确认）。

**改进建议**：MCP 工具集至少扩展为：`get_workflow`（读当前 schema + 当前 commit_id）、`create_workflow`、`save_workflow`（显式带 base_commit_id，做乐观锁）、`test_run_workflow`、`get_test_run_result`（轮询，返回节点级状态与错误）。工具返回统一结构化错误：`{error_code, retryable, field_path, message}`，让修复器能按字段定位。

#### 问题 5：目前缺哪些关键接口？哪些缺口会阻断自动修复？

**结论**：缺四个关键能力：详情读取、结果/日志查询、节点模板/字段字典、鉴权会话管理。其中前两个直接阻断自动修复，后两个阻断"稳定"。

**依据**：
- **结果/日志查询**：阻断修复的输入。没有它，不知道哪个节点失败、错误是什么，修复器只能盲改。
- **详情读取**：阻断编辑和 patch 的基线。没有它，拿不到当前完整 schema 和 `submit_commit_id`，也做不到方案承诺的"已有工作流编辑与修复"。
- **模板/字段字典**：阻断生成稳定性。目前只有 start/end/查询数据三个真实样例，LLM 生成分支、代码、LLM 节点时没有依据。
- **会话管理**：阻断长期运行。抓包里的 session 24 小时过期，没有登录/刷新机制，MCP server 跑一天就失效。

**风险**：save 失败的样例缺失导致"修复保存错误"无从设计；test_run 失败的真实错误结构缺失导致修复提示词无法设计。

**改进建议**：按优先级补：① 结果/日志查询（含轮询）→ ② 详情读取（含当前 commit）→ ③ 从平台导出节点类型与字段元数据 → ④ 会话登录/刷新。每一项缺失都会导致对应能力停留在纸面。

#### 问题 6：详情读取和日志查询是否是必须的？

**结论**：是，而且是**硬性必须**，不是"加分项"。

**依据**：
- 详情读取：编辑已有工作流的前提是拿到当前 schema 基线；save 的 `submit_commit_id` 必须从读取接口获得；局部 patch 本质是"读全图 → 本地最小修改 → 整图提交"，没有读取就没有 patch；回滚需要版本列表。
- 日志查询：验证闭环必须区分"发起成功"和"运行成功"；修复必须先定位失败节点；评估修复成功率必须有真实的失败/成功标签。方案自己的目标 2、3（修改已有工作流、自动修复）和模块 F（修复器）都依赖这两个接口，缺一个都不成立。

**风险**：不补的话，"闭环"就是单向管道，面试或落地时一被追问"你怎么知道它跑成功/失败在哪个节点"就塌了。

**改进建议**：把这两个接口列为 MVP 前置条件，而不是 Phase 2/3。在它们确认之前，MVP 范围应收缩为"生成 + 保存 + 发起试运行 + 人工查看控制台结果"。

#### 问题 7：schema 约束、节点模板化、最小 patch 策略是否合理？

**结论**：方向全部正确，但实现细节不足，尤其是"最小 patch"的机制描述是错的。

**依据**：
- schema 约束：方案只提了连通性、start/end 唯一性，缺**字段级白名单**（每类节点的必填/可选/枚举）和**变量作用域校验**（ref 必须指向真实上游 output）。从样例看，end 节点的 `inputParameters[].input.content` 引用 `blockID`，这正是最容易生成错的地方。
- 模板化：方向对，但模板必须**从真实平台导出**而不是手写——节点类型是数字编码，字段结构随平台版本变化。
- 最小 patch：save 接口提交的是**整个 schema 字符串**（从抓包确认），所以"局部 patch"在平台侧不存在，只能是"本地读全图 → 改一两个字段 → 整图提交"。真正的风险是**并发覆盖**和 **commit 过期**，方案完全没有提乐观锁。另外"保留历史版本"依赖平台的版本接口或自己持久化快照，方案没说要怎么存。

**风险**：把"局部 patch"理解成字节级 diff 是误解；没有乐观锁时，多人编辑会互相覆盖整图；模板化也可能导致模型只会拼模板，遇到模板外需求时硬造字段。

**改进建议**：校验器升级为三层：语法（JSON 可解析）→ 结构（字段白名单 + 必填 + 类型枚举）→ 语义（变量作用域、边连通、唯一 start/end、环检测）。patch 策略明确为"基线 commit 上的字段级修改 + base_commit_id 乐观锁 + 保存前快照"。模板库每个模板记录：类型 ID、必填/可选字段、输入变量、出边规则、已知坑。

#### 问题 8：有没有明显的工程风险、自相矛盾、或过度乐观？

**结论**：有，且不止一处。

**依据**：
1. **自相矛盾**：架构图包含"试运行结果分析"和"修复器"，8.2 又承认缺日志接口——闭环画了但前提没有，3、7 的流程描述把未实现的前提当成已具备。
2. **过度乐观**：8.1 说"生成+落库+验证已具备"，但"验证"实际是"发起试运行"，不是"确认运行成功"；8.3 说"自动修复闭环可行"没有依据，因为修复输入（错误日志）不存在。
3. **会话风险完全未提**：cookie session 24 小时过期，无登录/刷新机制，工具无法长期运行。
4. **异步语义未提**：test_run 是异步执行，轮询、超时、幂等都没设计。
5. **并发与误伤未提**：整图提交 + 无乐观锁，多人/多轮编辑互相覆盖；修复循环反复 save 也可能反复覆盖他人改动。
6. **"不编造字段"原则不可执行**：没有字段字典时这条原则只是口号。
7. **内部 API 无契约**：`coze.dev1.dachensky.com` 是非公开接口，字段可能随版本变化，`remaining_ttl`、`workflow_status`、`submit_commit_id` 语义全部未确认。
8. **数据安全/成本未提**：业务数据进 LLM、反复 test_run 的成本和审计。

**风险**：最大的是在缺日志接口的情况下开始写修复器，写完发现错误信息来源和预想不同，整个修复层返工。

**改进建议**：把方案分成两个诚实的产品阶段：A = 单向管道（生成+保存+试运行，人工看结果），B = 闭环（补读取/日志/字典后）。在 A 阶段就把 commit 语义、session 管理、并发策略确认清楚。

#### 问题 9：做成能上线的工具，最优先补哪 3 个能力？

**结论**：① 试运行结果/日志查询（含轮询）；② 工作流详情读取（含当前 commit/版本）；③ 平台节点模板与字段字典。

**依据**：这 3 个正好对应三个死穴：没有日志查询就没有修复输入；没有详情读取就没有编辑基线和 `submit_commit_id`；没有字段字典就没有"生成稳定性"和"不编造字段"的落地基础。其余（失败样例、会话管理、评估集）都是这 3 个的衍生品。

**风险**：如果只补接口 ①② 而跳过 ③，生成器会反复产出平台不认的 schema，修复器变成"修自己编造的错"。

**改进建议**：第 ③ 个做成"从平台导出 + 人工复核"的字典文件，每个节点类型一条：type ID、inputs 模板、outputs 声明、出边规则、常见错误。字典本身就是校验器和模板渲染器的单一数据源。

#### 问题 10：这个方案能否支撑 AI Agent 面试讲解？

**结论**：能，而且是很好的题材——但只撑得起"设计深度"，撑不起"闭环已实现"。

**依据**：覆盖了需求结构化、IR 分层、结构化输出、工具调用、工作流规划、错误修复、最小修改、工程化，知识点完整。最值得讲的点：
1. **为什么先规划再生成**——把随机性从"平台字段"收敛到"节点选择与参数"，这是工程判断，不是 prompt 技巧。
2. **LLM-IR-程序化渲染的三层分离**——确定性边界在哪里，是方案里最硬核的设计。
3. **"能发起 ≠ 能验证"**——用 execute_id 和真实日志的差距讲清闭环为什么必须补读取和日志接口。
4. **整图提交与最小 patch 的真相**——讲清"局部 patch 是本地改、整图提交、乐观锁防覆盖"，比空谈"最小修改原则"高级得多。
5. **平台契约不透明下的应对**——模板字典 + 白名单校验 + 错误分类 + 人工接管，这是真实工程里最常见的状态。

**风险**：面试官追问"修复失败怎么定位"时，如果方案没有日志接口，会暴露闭环是纸面的。诚实讲 MVP 边界反而加分。

**改进建议**：准备 2-3 个真实失败样例（save 失败、test_run 节点失败、commit 过期）和一套离线评估方式（golden 工作流集合，统计生成成功率、一次 save 成功率、修复轮次分布），面试时讲"怎么评估"比讲"怎么设计"更稀缺。

### 3. 必补项清单

**接口（先抓包确认）**
- 工作流详情读取：返回当前 schema、`workflow_status`、当前 `commit_id`/`submit_commit_id`、版本列表
- 试运行结果/日志查询：轮询接口、节点级状态、失败节点与错误信息、输出内容
- 会话：登录/刷新机制（cookie session 过期恢复）
- 可选：版本列表/回滚/发布接口

**样例**
- 一次完整的"读取当前 commit → save → test_run"真实请求响应，确认 `submit_commit_id` 从哪来
- save 失败样例：缺字段、类型错、commit 过期、schema 非法
- test_run 失败样例：节点级报错、依赖错误、超时
- 每个已知节点类型的完整模板：start、end、LLM、代码、条件分支、HTTP、数据库（目前只有 1/2/43 三个）
- `remaining_ttl`、`workflow_status`、`ignore_status_transfer` 的取值与含义

**规则**
- 节点类型白名单 + 每类必填/可选/枚举字段
- 变量作用域规则：ref 必须引用真实上游 outputs，`blockID` 必须存在
- 边规则：`sourceNodeID/targetNodeID`、分支/条件边的端口字段
- start/end 唯一、连通性、环检测（如果平台允许环，规则另定）
- commit 生命周期：读取→保存→试运行的 commit 语义与过期策略
- 修复边界：允许改的字段清单、禁止改的字段清单、每次修复前重新读基线

**测试**
- 校验器单测：合法/非法 schema 用例矩阵（字段、类型、变量引用、边）
- 模板渲染 golden tests：IR → schema 的确定性输出
- 端到端冒烟：create → save → test_run → 查结果
- 修复循环 mock 测试：模拟节点失败 → patch → 重试 → 收敛
- 并发/commit 冲突测试：两人同时编辑同一工作流
- 会话过期恢复测试

**信息缺口（影响判断，需要确认）**
- `submit_commit_id` 的来源与过期规则（直接影响 save 工具设计）
- test_run 结果获取方式（异步轮询接口路径与返回结构，直接影响整体闭环可行性的评级）
- 平台完整节点类型清单（目前只有 3 个样例，无法评估模板库规模）
- session 刷新机制（决定工具能否长期运行）
- 是否有多人协作/并发编辑需求（决定乐观锁是否是必选）
- 真实失败错误的结构（决定修复提示词和错误分类设计）

### 4. 设计修改建议

- **架构层**：改为状态机 `READ → PLAN → RENDER → VALIDATE → COMMIT → RUN → OBSERVE → REPAIR`，`REPAIR` 每次从 `READ` 重新开始（重新读基线）。横切三个模块：会话管理、版本快照/回滚、人工确认点（覆盖前）。把"试运行结果分析"从框图中拆成独立的 OBSERVE 层，明确它依赖日志接口。
- **工具层**：MCP 工具集扩展为 `get_workflow`、`create_workflow`、`save_workflow(base_commit_id)`、`test_run_workflow`、`get_test_run_result`（轮询）、`list_versions/rollback`。所有工具返回统一错误结构 `{error_code, retryable, field_path, message}`。会话管理做成工具链前置模块，过期自动续期，不能续期则拒绝操作并提示。
- **Prompt 层**：LLM 只输出两层——需求摘要和声明式 IR（节点类型枚举 + 参数表单值 + 边描述），平台 JSON 由代码渲染。IR 输出用 JSON Schema 强约束（response_format 或工具参数绑定）。修复提示词输入固定为：当前基线 schema、错误 `field_path`、失败节点上下文、允许修改的字段白名单。
- **校验层**：三层校验——语法（JSON 可解析）→ 结构（字段白名单、必填、类型枚举，依据字典）→ 语义（变量作用域、边连通、start/end 唯一、commit 有效性）。所有错误输出带 `field_path`，校验器同时作为"修复器能看懂什么"的契约。
- **修复层**：修复器输出"字段级 patch 计划"（`{op: replace/remove/add, target: field_path, value}`），由代码应用而不是让模型重写 schema；每次 patch 前重新读取最新基线；保存前生成快照；设置重试上限（建议 2-3 轮），超限转人工；以"日志接口返回运行成功"作为修复终止的唯一判据。

---

### 5. 最终建议

- **该不该按这个方案做**：按方案当骨架可以，但不要按方案当前的章节顺序执行。方案的"生成"部分可信，"修复"部分不可信。落地前先把第 3 节的信息缺口逐项确认，尤其是结果查询和详情读取两个接口。
- **先做什么**：① 抓包确认 `get_workflow`（或等价详情接口）和 test_run 结果查询接口的存在性与返回结构；② 确认 `submit_commit_id` 来源和 `remaining_ttl` 语义；③ 封装 MCP server（含会话管理），先手工构造一个 start→end→LLM 的最小可运行工作流跑通 create/save/test_run/查结果；④ 沉淀这 3-4 个节点的真实模板和字段字典；⑤ 写三层校验器；⑥ 最后才做修复循环，且用 mock 失败场景先测。
- **不建议做什么**：不建议在确认日志接口之前写修复器或宣称闭环；不建议让 LLM 直接输出最终平台 schema；不建议无乐观锁地自动 save（会整图覆盖他人改动）；不建议在模板字典缺失时追求"生成任意复杂工作流"；不建议把"发起试运行"包装成"验证通过"——无论对上线还是面试，这个区别都是方案目前最大的失分点。
