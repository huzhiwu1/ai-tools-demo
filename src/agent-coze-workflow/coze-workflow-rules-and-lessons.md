# Coze 工作流生成规则库 v1

> 来源：此前多次 Coze 工作流 JSON 生成、手工复制粘贴、试运行修复的实战经验。
>
> 用途：给“Coze 工作流自动生成 Agent”提供稳定的规则约束、模板化策略和修复依据，也可直接作为面试讲解素材。

---

## 1. 这份规则库解决什么问题

Coze 工作流不是普通 JSON，它是一个**有节点类型约束、出边规则、输出类型约束、导入兼容性约束**的图结构。

LLM 很容易在这里犯错，典型问题有：
- 节点缺字段
- 边连错
- 分支端口不合法
- 输出类型和声明不一致
- 粘贴后节点不连线
- 试运行报 BranchBuilder / schema 校验错误

所以这份规则库的作用是：

1. 让生成器少犯错
2. 让校验器能提前拦错
3. 让修复器知道怎么最小修改
4. 让 Prompt 有明确约束

---

## 2. 规则分层

建议在项目中把这些经验拆成 4 层：

### A. 硬规则（必须满足）
不满足就直接判失败，不允许进入 save/test_run。

### B. 软规则（强烈建议）
不一定致命，但会显著降低成功率。

### C. 生成策略（帮助 LLM 更稳）
不是平台硬约束，但能提高质量。

### D. 修复策略（失败后的最小修改原则）
用于自动修复或人工修复辅助。

---

## 3. 硬规则

### 3.1 每个节点必须有唯一 ID

#### 规则
- 所有节点 `id` 必须唯一
- edges 中引用的节点 ID 必须真实存在

#### 为什么重要
- 这是图结构最基础的正确性
- ID 重复或引用不存在，工作流直接坏掉

#### 典型坑
- LLM 复制模板时忘了改 ID
- edge 指向了不存在的节点

#### 校验方式
- `Set` 去重节点 ID
- 遍历 edges 校验 source/target 存在

---

### 3.2 起始节点和结束节点必须存在

#### 规则
- 工作流必须有 start 节点
- 工作流必须有 end 节点
- start/end 的连接必须形成有效路径

#### 为什么重要
- 没有起止节点，工作流不完整
- 有些平台 save 可能过，但 test_run 会挂

#### 典型坑
- LLM 只生成中间节点，漏了 end
- 图看起来像流程，实际没有终点

---

### 3.3 代码节点出边不要乱写 `sourcePortID`

#### 规则
- 代码节点（type=5）出边一律不要写 `sourcePortID`

#### 为什么重要
- 你已经实战踩过这个坑
- 一旦写了端口，Coze 可能构建 BranchSchema
- 代码节点不实现 BranchBuilder，会报错

#### 典型坑
- `sourcePortID: "default"`
- JSON 看似正常，试运行直接炸

#### 校验方式
- 检查所有代码节点的出边
- 发现 `sourcePortID` 直接报错或自动删除

---

### 3.4 LLM 节点分支规则必须按平台约定

#### 规则
- 大模型节点通常支持 `default` + `branch_error`
- 选择器节点通常支持 `true` / `false`
- 不同节点类型不能套用同一套分支逻辑

#### 为什么重要
- 分支规则不是装饰品，是平台语义的一部分
- 写错后经常是运行期错误，不是编译期错误

#### 典型坑
- 把代码节点当成可分支节点
- 把 LLM 节点的分支规则用到选择器节点上

---

### 3.5 节点输出类型必须和实际返回一致

#### 规则
- 节点声明的输出类型，必须和代码实际返回类型一致
- 不允许声明 object，实际返回 list；也不允许反过来

#### 为什么重要
- 这类错误常导致字段解析失败
- 后续节点拿到 null 或错误结构

#### 典型坑
- 代码节点返回 list，但 schema 声明 object
- 最终输出字段被置空

#### 校验方式
- 静态检查节点模板的 `outputType`
- 对代码节点可做最基本的返回结构约束提示

---

### 3.6 每个节点都要有 `_temp`

#### 规则
- 手工生成 / 复制节点时，必须保留 `_temp`
- `_temp` 通常包含 `bounds`、`externalData`

#### 为什么重要
- 少了 `_temp`，粘贴导入后可能不连线
- 这是 Coze JSON 导入兼容性的大坑

#### 典型坑
- 手动新增节点后漏了 `_temp`
- 粘贴到 Coze 平台后节点散开、连线消失

#### 校验方式
- 节点模板里强制包含 `_temp`
- 生成前检查 `_temp` 是否存在

---

### 3.7 复制模板节点后必须更新 `_temp.bounds`

#### 规则
- 从模板 deep copy 后，要更新坐标
- 不能让多个节点共用旧坐标

#### 为什么重要
- 不改坐标，导入后节点叠在一起，画布混乱
- 也容易影响平台识别

---

### 3.8 边两端节点必须存在

#### 规则
- 所有边的 source / target 都必须指向真实节点

#### 为什么重要
- 这是最基本的图合法性
- 不合法会导致 save/test_run 失败

---

## 4. 软规则

### 4.1 优先少节点、强聚合

#### 规则
- 能合并就合并
- 能少拆就少拆

#### 为什么重要
- 节点越多，协调成本越高
- 容易出现 dayLabel、批次、变量引用错位

#### 经验来源
- 你之前的 Coze 工作流里，多节点拆分曾引发协调和错位问题
- 单节点聚合有时更稳

#### 适用场景
- 批处理
- 信息抽取
- 简单串行流程

---

### 4.2 优先使用模板，而不是从零发明

#### 规则
- 生成器优先匹配已有模板
- 只填参数，不完全自由发挥

#### 为什么重要
- 模板比自由生成更稳定
- 也更容易人工审查

---

### 4.3 先规划草图，再输出最终 JSON

#### 规则
- 先生成 nodes / edges 草图
- 再映射到 Coze schema

#### 为什么重要
- 能减少 schema 漂移
- 方便定位问题在“规划”还是“映射”

---

### 4.4 本地先校验，再发 Coze

#### 规则
- 先跑 validator
- 校验过了再 save/test_run

#### 为什么重要
- 省掉大量无意义请求
- 提前拦截明显错误

---

## 5. 生成策略

### 5.1 结构化输出优先

#### 建议
LLM 每一步都输出 JSON，不要夹解释文本。

#### 原因
- 便于程序解析
- 便于链式处理
- 便于调试和回放

---

### 5.2 任务拆成三步

#### 建议流程
1. 需求解析
2. 草图规划
3. Coze schema 生成

#### 原因
- 减少单步复杂度
- 让每一步都更容易纠错

---

### 5.3 节点模板化

#### 建议模板
- start
- end
- llm
- code
- condition / branch
- database query
- http request

#### 原因
- 降低随机性
- 提高生成质量
- 方便做白名单约束

---

### 5.4 节点数量上限建议

#### 建议
MVP 阶段尽量控制在少节点。

#### 原因
- 节点越多，越难保证连线和数据流正确
- 先跑通主链路更重要

---

## 6. 修复策略

### 6.1 先定位，再最小修改

#### 规则
- 修复时不要重写整张图
- 先找出具体出错节点或边
- 只改最小必要部分

#### 为什么重要
- 整图重写很容易引入新 bug
- 最小 patch 更容易验证

---

### 6.2 错误信息要引用“最终处理后的数据”

#### 规则
- 错误节点、提示文案、输出内容要引用最终复检后的数据
- 不要引用旧状态或前一轮中间结果

#### 为什么重要
- 你之前实战中踩过“错误节点引用旧数据”的坑
- 会导致用户看到过时错误信息

---

### 6.3 修复后必须重新试运行

#### 规则
- 任何修复都必须重新 test_run
- 不允许只 save 不验证

#### 为什么重要
- save 成功不代表执行正确
- Coze 的坑很多是运行期才暴露

---

## 7. Prompt 约束可以直接写进系统提示词

### 建议写进 Prompt 的规则
- 不允许编造未知字段
- 优先使用模板
- 先规划草图，再输出 JSON
- 代码节点出边不要加 `sourcePortID`
- 输出类型要一致
- 节点数量尽量少
- 修复时只做最小修改

### 作用
- 降低模型胡写概率
- 让生成结果更接近可执行状态

---

## 8. 适合放进代码里的校验点

### validator 必做
- JSON 是否可 parse
- 节点 ID 是否重复
- start/end 是否存在
- 边是否引用不存在节点
- `_temp` 是否存在
- 代码节点是否含非法端口字段
- 输出类型是否一致

### validator 可选
- 节点类型白名单
- 节点数量控制
- 分支规则检查
- 常见模板字段完整性检查

---

## 9. 适合放进模板库的内容

### 9.1 节点模板
每种常见节点先做模板：
- 开始
- 结束
- LLM
- 代码
- 条件分支
- 查询节点

### 9.2 输出模板
- object 输出
- list 输出
- string 输出

### 9.3 错误模板
- schema 错误
- 节点缺失
- 边引用错误
- BranchBuilder 错误
- 输出类型不匹配

## 10. 这份规则库怎么用于项目

### 生成阶段
- 作为 LLM 的约束输入
- 作为草图到 JSON 的映射依据
- 作为生成前的本地校验规则

### 修复阶段
- 作为错误分类依据
- 作为最小 patch 的边界
- 作为重试策略的判定条件

### 面试阶段
- 作为项目经验总结
- 作为“为什么这样设计”的论据

## 11. 最值得记住的 7 条

1. 代码节点出边不要写 `sourcePortID`
2. `_temp` 不能丢
3. 节点 ID 必须唯一
4. 边两端节点必须存在
5. 节点输出类型必须一致
6. 先草图，再 JSON
7. 修复只做最小 patch
