# Agent 框架选型与效果评估

## 要不要用框架？

写 Agent 有三种路线：

| 路线 | 优点 | 缺点 | 适合 |
| ---- | ---- | ---- | ---- |
| 裸写循环（自己调 LLM API + while） | 完全可控、无依赖 | 状态管理、中断、重试全要自己造 | 学习 / 极简单场景 |
| 通用框架（LangChain / LangGraph） | 生态全、图编排、checkpointer、interrupt 开箱即用 | 抽象层多、版本升级折腾 | 中大型项目 |
| 多 Agent 框架（CrewAI / AutoGen / 等） | 开箱即用的角色/协作 | 抽象重、黑盒多 | 明确需要多角色协作 |

本项目选了 **LangGraph**，看重的正是它解决 Agent 工程的核心痛点：**有状态的图执行 + 中断/恢复 + 流式输出**。

## LangGraph 的核心模型：状态图

传统代码是"函数调用栈"，LangGraph 是**显式状态图**：

```
   ┌────┐    ┌─────────┐    ┌─────────┐
   │agent│──►│  tools  │──►│  agent  │──► ... ──► END
   └────┘    └─────────┘    └─────────┘
     ▲                            │
     └─────────── 循环 ───────────┘
```

三个关键概念：

1. **State（状态）**：图执行过程中共享的数据，LangGraph 自动做"增量更新"（merge）
2. **Nodes（节点）**：执行的函数，如 agent（调 LLM）、tools（执行工具）
3. **Edges（边）**：路由逻辑，如"有 tool_calls 就回到 agent，没有就 END"

`createReactAgent` 就是官方预置好的 ReAct 状态图。本项目的复用方式（`react-agent.service.ts`）：

```ts
const agent = await createReactAgent({
  llm,
  tools: ALL_TOOLS,
  checkpointer: new MemorySaver(),      // 状态持久化
  stateModifier: systemPrompt,          // 注入系统提示词
});
```

然后通过 `streamEvents` 消费事件流，实现前端流式展示。

## 框架带来的三个工程能力

### 1. Checkpointer：状态可恢复

没有框架时，"执行到一半进程重启"意味着全部重来。LangGraph 的 checkpointer 把状态落盘，配合 `thread_id` 可以恢复到任意断点——这是 interrupt/resume 的基础。

### 2. interrupt/resume：人机协作

第 2 篇讲过：Agent 可以暂停等用户输入，这在真实产品里是刚需（澄清、审批、确认）。裸写循环要实现这个很痛苦，框架内置。

### 3. 流式事件：用户可感知

Agent 任务动辄几十秒，没有流式输出用户会以为卡死。框架统一输出事件流（思考增量、工具调用、中断），前端拿到什么渲染什么。

## 框架选型的现实建议

1. **先跑通，再抽象**：第一版直接用框架预置组件（createReactAgent），别急着自定义图
2. **别迷信框架的"万能"**：业务逻辑（校验、缓存、迭代上限）还是要自己写，框架只管编排
3. **关注升级成本**：LangChain/LangGraph 版本间 API 变动频繁，锁定版本并写集成测试
4. **多 Agent 不是必须**：单 Agent + 工具也能覆盖大部分需求，多 Agent 只在角色边界清晰时才有收益

## 怎么评估一个 Agent 好不好

Agent 无法用"单测通过"衡量，需要多维度指标：

| 维度 | 指标 | 本项目例子 |
| ---- | ---- | ---------- |
| 成功率 | 任务完成率、一次通过率 | 工作流一次生成且校验通过的比例 |
| 质量 | 产物质量、准确率 | batch_validate 的 accuracy |
| 效率 | 迭代轮数、token 消耗、耗时 | 平均 2.4 轮修复达到 100% |
| 自主度 | 无需人工介入的比例 | 澄清次数、失败后求助次数 |
| 成本 | 单任务 token/费用 | 句柄化省了多少 token |
| 安全性 | 越权操作、错误重试率 | 凭证错误是否被正确分类 |

### 评估方法

1. **固定评测集**：收集 30-50 个真实需求 + 期望结果，每次改动跑一遍，看成功率变化
2. **行为不变量测试**：不测输出文本，测"行为规则"（如"每次保存前必过校验"）
3. **回归失败集**：把历史上失败的 case 单独建集，防止"修了 A 破了 B"
4. **人工抽检**：LLM 自评有偏差（自己出题自己考），定期人工复核

## 从 Demo 到生产

| 阶段 | 重点 |
| ---- | ---- |
| Demo | 跑通 ReAct 循环 + 核心工具 |
| 内测 | 补校验、错误分类、流式输出、会话管理 |
| 生产 | 持久化 checkpointer、日志留存、评测集回归、限流与成本控制、人工审核节点 |

## 核心要点

- 框架的价值在状态管理、中断恢复、流式事件，不在"魔法"
- LangGraph 是显式状态图：State / Nodes / Edges 三件套
- 先用预置组件跑通，再按需自定义
- Agent 评估用多维指标：成功率、质量、效率、成本、安全
- 固定评测集 + 失败回归集 + 人工抽检，是 Agent 持续迭代的基准线

## 延伸思考

- 你的 Agent 上线后，用户需求分布会漂移（"评测集过时"）。怎么持续更新评测集？（提示：线上日志回流 + 人工标注）
- 如果单 Agent 调用 20 个工具开始混乱，是加提示词、工具分组，还是拆多 Agent？判断依据是什么？
