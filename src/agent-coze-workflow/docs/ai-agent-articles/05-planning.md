# 规划：从"走一步看一步"到"先想后做"

## 为什么需要规划

纯 ReAct 是"贪心算法"：每一步只做当下最好的决定。任务简单没问题，但复杂任务会踩坑：

- 生成 8 节点的工作流，边写边想，写到第 5 个节点发现第 2 个节点的输出对不上
- 工具调了一大堆，最后发现方向从一开始就错了，token 全浪费
- 模型"走一步看一步"时容易被中间噪音带偏，忘了最终目标

规划（Planning）的思路是：**先想清楚整体方案，再动手执行，执行中按计划推进。**

## 规划与执行分离

本项目把"设计"和"生成"拆成了两个工具：

```text
plan_workflow      → 分析需求，输出结构化规划（steps + contracts + 约束）
generate_workflow  → 把规划映射成 Coze 平台可部署的 JSON
```

为什么必须拆？因为两个任务对模型的要求完全不同：

| 任务 | 难点 | 失败代价 |
| ---- | ---- | -------- |
| 规划 | 理解需求、拆解步骤、定义数据契约 | 方向错了后面全错 |
| 生成 | 精确遵守平台 schema、字段对齐 | 校验失败，可以重来 |

先规划再生成，等于给 Agent 装了一个"先画图纸再施工"的流程。图纸错了，改图纸的成本远低于拆了重建。

## 两段式规划：先骨架，再填肉

项目里规划本身还分两段（见 `apps/api/src/prompts/plan-prompt.ts` 的 `PLAN_SKELETON_PROMPT`）：

**Stage 1 骨架**：只输出元信息 + steps（含输入输出契约），不输出 nodeConfig：

```json
{
  "needClarification": false,
  "name": "song_search",
  "steps": [
    {
      "nodeType": "code",
      "description": "根据歌名查询歌词",
      "dependencies": [-1],
      "contract": {
        "inputs": [{"name": "user_input", "source": "用户输入"}],
        "outputs": [{"name": "result", "type": "string"}]
      }
    }
  ]
}
```

**Stage 2 逐节点配置**：基于骨架，逐个节点填充详细配置。

这样做的原因：

1. **先对齐全局**：骨架阶段先保证"节点顺序、变量名全局一致"，避免下游引用了不存在的上游输出
2. **缩小单次输出**：一次输出几百行 JSON 容易崩，拆开每次只做一小块，成功率大幅提升
3. **尽早发现方向错误**：骨架不对时，还没写配置就已经暴露

这是"分步生成"（step-by-step generation）在工程上的直接应用：**把一个大输出拆成多个小输出，每个小输出都有明确的输入和校验点。**

## 规划里的澄清机制

规划的输入是用户需求，而用户需求经常信息不全。所以规划器设计成**两段式**：

```text
需求不明确 → 返回 needClarification=true + 澄清问题 → 用户回答 → 重新规划
需求明确   → 返回完整规划
```

这对应到 ReAct 层的 `clarify_question` 工具（interrupt 暂停等用户）。规划器内部和 Agent 层都有澄清能力，形成双保险：

- Agent 层：发现信息缺，先问再规划
- 规划器层：LLM 直接给的规划不完整，再问

## 规划完成与"不要重复规划"

Agent 的常见毛病是**反复规划**：plan 完了不执行，又去 plan 一遍，像开会不干活。项目用 `planningComplete` 标志 + 提示词约束：

> plan_workflow 返回 planningComplete=true 后，直接进入 generate_workflow（传 planId）。除非规划结果与用户需求明显不符（如漏了关键步骤/选错模型），否则不要再次调用 plan_workflow。

这里体现了 Agent 工程的一个重要原则：**给 Agent 的"自主性"画边界**。自主不等于无限自由，明确的流程约束（"规划一次 → 生成 → 部署 → 验证"）反而让 Agent 更可靠。

## 规划对象的粒度

规划不只能规划"步骤"，还能规划：

| 规划维度 | 例子 |
| -------- | ---- |
| 步骤顺序 | 先查询、再处理、最后格式化输出 |
| 数据契约 | 每个节点的输入输出字段名、类型 |
| 资源选择 | 用哪个模型、查哪个数据库（get_platform_facts） |
| 约束与风险 | 字段长度限制、分支条件、易错点提示 |

本项目的 `contract` 机制很有意思：它把"变量名必须全局对齐"从"模型自觉"升级成了**结构约束**——每个 step 的 inputs 必须匹配上游 outputs，校验器可以程序化检查。这是规划从"prompt 里的软要求"变成"schema 里的硬约束"的典范。

## 核心要点

- 规划与执行分离：先画图纸再施工，方向错了改图纸比拆房便宜
- 大输出拆小：骨架 → 逐节点配置，每次只做一小块，成功率更高
- 规划阶段就要定义数据契约（contracts），让"变量对齐"变成可校验的约束
- 澄清机制贯穿规划和执行两层，信息不全先问
- 给 Agent 画边界：规划完成即进入执行，禁止无意义重复规划

## 延伸思考

- "规划"本身要不要让模型做？——固定模板 + 少量模型填充可能更稳，规划器的复杂度要匹配任务复杂度。
- 如果规划被校验器驳回，是重新规划还是局部修改？本项目的答案是局部修复（见第 7 篇），思考为什么局部优于全量。
