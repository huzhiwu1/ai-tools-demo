# Agent 可靠性工程：让"会犯错的大脑"稳定交付

## 为什么 Agent 特别需要可靠性工程

传统软件的错误是确定的：要么对，要么错，测试能覆盖。Agent 的错误是**概率性的**：

- 同样的输入，两次可能走不同的路径
- 模型可能误判"任务已完成"
- 工具执行成功但结果不符合预期

所以 Agent 的可靠性不能靠"写对代码"，要靠**分层防御 + 验证闭环**。

## 失败模式清单

先盘点 Agent 系统可能怎么挂（本项目实战总结）：

| 失败层 | 典型表现 |
| ------ | -------- |
| 理解层 | 误解需求、漏掉关键约束 |
| 规划层 | 步骤缺失、依赖错误、变量名对不上 |
| 生成层 | JSON 不合 schema、节点字段缺失、边连错 |
| 执行层 | 平台接口报错、凭证过期 |
| 验证层 | 试运行失败、准确率不达标 |
| 状态层 | 改了没保存、平台被并发修改 |

每一层都需要对应的兜底，单靠"模型聪明"是不行的。

## 第一道防线：Prompt 约束

最便宜的一层。系统提示词把规则写得像"员工手册"：

- 流程约束："规划→生成→部署→试运行→验证，按顺序执行"
- 分支约束："信息不完整先 clarify_question"
- 错误语义："凭证错误不要改工作流，告知用户检查 .env"
- 状态约束："修改后必须 save_to_coze 保存才生效"

但 Prompt 约束是**软约束**——模型可能违反。所以它只是第一道防线，不是最后一道。

## 第二道防线：Schema 与本地校验

把规则变成**硬约束**。本项目有完整的 schema 体系：

- 工具参数用 Zod schema（`z.object(...)`），参数不对直接报错
- 工作流结构有类型定义（`packages/workflow-schema`）
- 生成后有本地校验器 `validateWorkflow`：节点必填字段、依赖拓扑、输出类型

校验失败不直接放弃，而是作为 Observation 回灌，走修复流程。这里有个重要设计：**本地校验在保存之前**，把错误拦截在"还没污染平台"的阶段。

## 第三道防线：验证闭环（最关键）

校验只保证"结构对"，不保证"功能对"。所以项目设计了 `batch_validate` 工具：

```text
构造测试用例（LLM 根据需求/文件内容生成）
→ 批量试运行
→ 计算 accuracy
→ 失败用例按 failurePatterns 归因分组
→ 给修复指令 fixInstruction
→ update_workflow 修改
→ save_to_coze 保存
→ 再 batch_validate
```

这是把"测试驱动开发"搬到了 Agent 系统里：**每个 Agent 交付都要过一遍自动化验收**。准确率 < 100% 就进入"修改 → 重验"循环。

这个闭环还包含"休止符"：

> batch_validate / update_workflow 有系统级迭代上限（3 轮），达到后必须停止并汇报结果，不要尝试绕过。

**给自动修复设上限**，防止"修不好就一直修"烧钱，同时把控制权交回用户。

## 错误分类：决定"要不要重试"

Agent 的"执着"要分情况：

| 错误类型 | 例子 | 策略 |
| -------- | ---- | ---- |
| 可重试 | JSON 解析失败、接口 500 | 回灌模型，修正重试 |
| 可修复 | 校验失败、试运行失败 | 走修复闭环 |
| 不可修复 | 凭证过期、权限不足 | 停止，告知用户 |

项目里把凭证错误写成了系统级约束，防止 Agent 在错误方向上浪费 token 和时间：

> "authentication failed" → 这是平台凭证问题，不是工作流问题！不要修改工作流、不要反复保存。

## 可观测性：能看到 Agent 在想什么

概率性系统必须可观测，否则无法排查。本项目通过 SSE 流式输出事件：

- `text`：LLM 思考文本（用户能看到"它正在干什么"）
- `tool_start` / `tool_end`：工具调用过程
- `interrupt`：暂停等用户
- `done` / `error`：结束与异常

配合 [ReAct 思考链路全景图](../react-agent-thinking-chain.md) 这种"思考链路全景图"，排障时可以一步步对照"模型在这个节点应该做什么、实际做了什么"。

## 测试策略

Agent 系统测试分三层：

1. **单元测试**：工具、操作、转换器的确定性逻辑（如 `apply-operation.spec.ts`）
2. **集成测试**：用 mock 的平台接口跑完整链路，验证流程编排
3. **回归测试**：保留历史失败用例（"这个需求曾经生成失败过"），防止模型升级或提示词改动后旧病复发

注意：**不要用固定快照测试 LLM 输出**（输出天然不稳定），要测"行为不变量"——比如"保存前必须经过本地校验"。

## 核心要点

- Agent 错误是概率性的，可靠性靠分层防御，不靠模型自觉
- 四道防线：Prompt 约束 → Schema/本地校验 → 验证闭环 → 错误分类
- 验证闭环（批量试运行 + 准确率 + 归因修复）是"Agent 的自动化验收"
- 自动修复必须设迭代上限
- 可观测性（流式事件 + 思考链路）是排障的前提

## 延伸思考

- 如果 batch_validate 的用例是 LLM 自己构造的，会不会"自己出题自己考"？如何降低这种偏差？（提示：人工抽查、保留真实用户用例）
- Agent 上线后，哪些日志值得长期留存？（提示：失败路径、修复后的最终方案，这是产品最宝贵的语料）
