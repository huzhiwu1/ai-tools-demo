# 记忆与状态管理：Agent 的档案柜

## 一个常见误解

"LLM 有记忆"是错觉。每次调用模型都是无状态的：它看到什么上下文，就基于什么回答。所谓"记忆"，其实是**工程上把历史数据重新拼进 prompt**。

所以 Agent 的记忆问题，本质是三个问题：

1. 哪些历史要拼进去？（短期记忆）
2. 哪些历史要长期保存、随时取用？（长期记忆）
3. 执行到一半的状态放哪、怎么恢复？（工作状态）

## 三层记忆模型

| 层级 | 内容 | 存储位置 | 生命周期 |
| ---- | ---- | -------- | -------- |
| 短期记忆 | 当前对话的 messages | 上下文窗口 / 服务端消息数组 | 本次会话 |
| 工作状态 | planId、workflowId、验证轮次 | checkpointer / 服务端缓存 | 任务执行期间 |
| 长期记忆 | 平台已有工作流、用户偏好、规则 | 数据库 / 平台 API / 缓存文件 | 跨会话 |

## 短期记忆：对话历史

最简单也最容易失控。本项目两种方式并存：

- **messages 数组**：每轮把历史消息拼进下一次 LLM 调用
- **checkpointer**：LangGraph 用 `MemorySaver` 按 `thread_id` 自动恢复状态

```ts
// apps/api/src/agent/react-agent.service.ts
// 每个会话创建独立的 graph 实例（含 MemorySaver checkpointer）
// 多轮对话：messages 拼入 history，checkpointer 按 thread_id 自动恢复状态
```

短期记忆的经典问题是**上下文窗口溢出**。对策方向：

- 截断最旧的消息
- 把中间产物"摘要化"（对话太长时先总结再继续）
- 工具返回值不要全量塞进历史（见第 3 篇的"返回值精简"）

本项目里有个很典型的省 token 设计：`read_workflow` 默认 `scope=overview`，只有需要完整配置时才 `scope=full`。**按需取数据，而不是一次全拉。**

## 工作状态：任务进行中的"草稿纸"

一个生成工作流任务，中间状态包括：planId、workflow JSON（在服务端缓存）、workflowId、验证轮次。这些如果全让模型"记着"，必然出错。

本项目的做法：

1. **句柄化**：重状态放服务端，模型只持有短 ID（planId / workflowId）
2. **服务端缓存**：`workflow-cache.ts` 持有"正在编辑的工作流"，`update_workflow` 只改缓存不落平台，`save_to_coze` 才真正保存
3. **checkpointer 持久化中断点**：`interrupt()` 时图的执行状态被 checkpoint 住，resume 后从断点继续

这个"草稿纸在服务端、模型只拿引用"的模式，是整个系统稳定性的基石。

## 长期记忆：跨会话的能力

本项目最有意思的长期记忆是 `list_workflows` / `read_workflow` 工具：

- 用户说"改一下之前那个工作流"，Agent 记不住"之前"是哪个
- 但平台上有！所以 Agent 通过 `list_workflows`（按名称搜索）找回 workflowId，再用 `read_workflow` 读取说明书
- 读完后写入服务端缓存，后续修改基于这份最新说明书

系统提示词里写着：

> 如果用户提到"之前的工作流/已经保存的/改一下刚才那个"，但当前上下文没有 workflowId，先 list_workflows 按名称搜索找回，不要重新创建。

这就是长期记忆的工程化形态：**记忆不一定要存在 Agent 内部，可以做成"检索工具"，需要时现查。** 平台就是数据库，工具就是查询接口。

## 记忆一致性：最容易翻车的点

Agent 系统里 90% 的"状态错乱"来自记忆不同步：

### 场景一：改完没保存

`update_workflow` 只改了服务端缓存，如果模型直接回复"已修改"而不调 `save_to_coze`，用户看到的就是"白改了"。系统提示词强制：

> update_workflow 只改服务端缓存不落平台，修改后必须 save_to_coze（传 workflowId）保存，保存成功才生效。

### 场景二：平台被别人改了

`save_to_coze` 返回"线上工作流已被修改，已重新拉取"——说明平台侧有人工修改。此时必须基于最新版本重新描述修改指令，而不是拿旧缓存硬写。

### 场景三：MemorySaver 不跨实例

```ts
// react-agent.service.ts 注释
// MemorySaver 不支持跨实例恢复，每个会话必须缓存独立的 graph
```

MemorySaver 是内存态，进程重启就没了，多实例部署时更不可用。生产环境要换持久化 checkpointer（如 SQLite/Redis），且要设计好 `thread_id` 的归属规则。

## 记忆管理的三条原则

1. **能不记就不记**：状态放在代码侧（服务端缓存），模型只拿引用
2. **按需取用**：overview 先看，full 再拉；别把所有历史塞进上下文
3. **一致性优先**：任何"改"都对应一个"落盘"动作，且要处理"被别人改过"的并发冲突

## 核心要点

- LLM 无记忆，记忆是工程拼出来的
- 三层记忆：短期（对话历史）、工作状态（checkpointer/缓存）、长期（检索工具）
- 句柄化 + 服务端缓存 = 状态稳定；全塞 prompt = 必然出错
- 记忆一致性（保存、并发、跨实例）是 Agent 稳定性的大头
